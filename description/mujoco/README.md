# Modular MuJoCo Scenes

Each `scene*.xml` is a small composition of one robot, one background and optional terrain/object includes, plus its simulation timestep.

```text
description/
  meshes/
    robots/g1/
    robots/h2/
    terrains/unit_wedge.stl
  mujoco/
    mujoco_scene_creator.py
    common/backgrounds/
    common/materials/
    robots/g1/{g1_29dof.xml,scene.xml,scene_flat.xml,scene_ramp.xml,scene_uneven.xml}
    robots/h2/{h2_31dof.xml,scene.xml,scene_flat.xml,scene_ramp.xml,scene_uneven.xml}
    terrains/
    objects/
    textures/
  urdf/
    robots/g1/
    robots/h2/
    terrains/{stairs,ramp}.urdf.xacro
    terrains/uneven_terrain.urdf
    objects/boxes.urdf.xacro
config/
  terrains/{stairs,ramp,uneven_terrain}_params.yaml
  objects/boxes_params.yaml
```

Each description format owns its robot and environment modules rather than grouping different formats inside one robot directory.
MuJoCo robot files live in `description/mujoco/robots/<robot>/`, URDF files in `description/urdf/robots/<robot>/`, and shared meshes in `description/meshes/robots/<robot>/`.
The RViz staircase belongs to `description/urdf/terrains/`, and its format-neutral parameters belong to `config/terrains/`, not MuJoCo.

| Module | Contents |
| --- | --- |
| `robots/g1/g1_29dof.xml` | Robot bodies, joints, actuators and sensors; meshes live in `description/meshes/robots/g1/` |
| `robots/h2/h2_31dof.xml` | Official Unitree H2 with matching URDF pelvis inertia and sole frames; meshes live in `description/meshes/robots/h2/` |
| `common/backgrounds/background_day.xml` | Original daytime sky, lighting, camera and physical floor |
| `common/backgrounds/background_night.xml` | Studio lighting, camera, satin floor and robot finish |
| `common/materials/terrain_materials.xml` | Shared matte material using `textures/studio_terrain.png` |
| `terrains/stairs.xml` | Stair geometry generated from `stairs.xml.xacro` using `../../config/terrains/stairs_params.yaml` |
| `../urdf/terrains/stairs.urdf.xacro` | Matching RViz environment geometry using the same staircase parameters |
| `terrains/ramp.xml` | Solid wedge ramp (flush entry, vertical far end) generated from `ramp.xml.xacro` using `../../config/terrains/ramp_params.yaml` (position, yaw, horizontal length, incline, width) |
| `../urdf/terrains/ramp.urdf.xacro` | Matching RViz wedge: `../meshes/terrains/unit_wedge.stl` scaled by length, width and rise from the same parameters |
| `terrains/slope.xml` | Original separate 5-degree slope |
| `terrains/uneven_terrain.xml` | Seeded rolling/random blocks generated by `terrains/generate_uneven_terrain.py` from `../../config/terrains/uneven_terrain_params.yaml`; uses the stair texture |
| `../urdf/terrains/uneven_terrain.urdf` | Matching RViz blocks, field pose and exact clear patch generated from the same parameters |
| `objects/boxes.xml` | Movable boxes generated from `boxes.xml.xacro` using `../../config/objects/boxes_params.yaml` (count, names, poses, sizes, masses, inertias, colours) |
| `../urdf/objects/boxes.urdf.xacro` | Matching RViz boxes at their spawn poses from the same parameters |

Both backgrounds include `../materials/terrain_materials.xml` once, so multiple terrains can coexist without duplicate material definitions.
Terrain modules assign `material="studio_terrain"` to their geoms; they do not copy lighting or texture assets.
The robot module contains no background or terrain definitions.

For example, `robots/g1/scene.xml` can combine the night background, G1, stairs and boxes:

```xml
<mujoco model="g1_custom_scene">
  <include file="g1_29dof.xml"/>
  <include file="../../common/backgrounds/background_night.xml"/>
  <include file="../../terrains/stairs.xml"/>
  <include file="../../objects/boxes.xml"/>
  <option timestep="0.0001"/>
</mujoco>
```

Select exactly one background and include each terrain module at most once.
Keep scene entry points next to their robot module in `description/mujoco/robots/<robot>/` because MuJoCo resolves compiler directories from the top-level scene, while nested XML includes resolve from the including file.
Each robot module uses `meshdir="../../../meshes/robots/<robot>"` and `texturedir="../../"`, so shared textures remain in `description/mujoco/textures/`.
These paths also work in the installed package because CMake installs both the `description/` and `config/` trees.
The floor's size, friction and priority are identical in both backgrounds.
Terrain dimensions, contact properties, inertias and actuator settings are independent of the background choice.

Entry points are `scene.xml` (night/configured terrain), `scene_flat.xml` (day/flat), `scene_ramp.xml` (night/ramp) and `scene_uneven.xml` (night/uneven field).
Choose one through `robot.launch.py robotName:=g1 mujocoModelFile:=scene.xml`, or use `robotName:=h2` with the same scene name.
The launch keeps the selected robot's scene, URDF and controller configuration together; an absolute scene path remains available as an explicit override.
Switch day/night by changing the scene's background include; separate scene files for each appearance are unnecessary.

From the package root, the generator can compose scenes and regenerate night appearance assets:

Use `--terrain rough` to select `terrains/uneven_terrain.xml`, `--terrain boxes` for the movable boxes, or `--terrain none` to use only the background floor.

```bash
python3 description/mujoco/mujoco_scene_creator.py
python3 description/mujoco/mujoco_scene_creator.py --reference scene_ramp.xml
python3 description/mujoco/mujoco_scene_creator.py --robot-name h2 --reference scene_ramp.xml
python3 description/mujoco/mujoco_scene_creator.py --terrain stairs boxes -o scene_objects.xml
python3 description/mujoco/mujoco_scene_creator.py --background day --terrain ramp -o scene_day_ramp.xml
```

The default command updates `robots/g1/scene.xml` and the shared `common/backgrounds/background_night.xml`; every night scene immediately uses that appearance.
`--robot-name h2` selects `robots/h2/`, and relative reference/output scene paths are resolved within that robot directory.
With `--reference`, the selected reference scene is updated unless `--output` is supplied.
Appearance overrides such as `--reflectance 0.02` write a background named after the output scene in `common/backgrounds/`, leaving the shared night preset intact.
Change the generator's `STYLES` and `STUDIO_LIGHTS` to tune the night appearance; edit `common/backgrounds/background_day.xml` for daytime settings and `common/materials/terrain_materials.xml` for terrain texture scale/specularity.
Regenerating stairs, the ramp or the boxes through xacro retains the material assignment, and all scenes immediately use the regenerated geometry without rerunning the scene generator.
Each generated file's xacro header gives its command, for example:

```bash
cd description/mujoco/terrains && xacro ./ramp.xml.xacro ramp_params_file:=../../../config/terrains/ramp_params.yaml -o ./ramp.xml
cd description/mujoco/objects && xacro ./boxes.xml.xacro boxes_params_file:=../../../config/objects/boxes_params.yaml -o ./boxes.xml
```

In RViz, select the matching environment with `environmentDescription:=<pkg_share>/description/urdf/terrains/ramp.urdf.xacro` (or `objects/boxes.urdf.xacro`); the launch passes all three parameter files, and each xacro reads its own.

For the uneven field, edit [the shared YAML](../../config/terrains/uneven_terrain_params.yaml), then regenerate both formats:

```bash
python3 description/mujoco/terrains/generate_uneven_terrain.py
python3 description/mujoco/terrains/generate_uneven_terrain.py --check
```

See [uneven-terrain parameters](../../config/terrains/README.md#uneven-terrain) for height-difference bounds, profile, seed, center, grid and clear-patch semantics.
The old fixed-size `uneven_terrain_10x10.xml` name is removed; use `uneven_terrain.xml` independently of the configured footprint.
The generated RViz file is ordinary URDF, which the existing `environmentDescription` xacro command also accepts; no launch arguments were added.

Validate the layout from the package root with `python3 -m unittest discover -s tests -p test_mujoco_scene_layout.py -v`.
MuJoCo and xacro checks run when their Python packages are installed; the remaining resource-path checks need only the standard library.
